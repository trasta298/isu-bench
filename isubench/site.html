Can a coding agent make a slow web service fast, without breaking it?

遅いWebサービスを、壊さずにどこまで速くできるか

isu-bench hands an agent a web service it has never seen, the three servers it runs on, and {RUNS} load tests. There is no time limit, no hint and no one to ask. The {RUNS}th load test is its score.

isu-benchは、コーディングエージェントに初めて見るWebサービスと、それが動く3台のサーバーを渡します。ベンチマークを実行できるのは{RUNS}回だけ。時間制限もヒントもなく、質問できる相手もいません。{RUNS}回目の点がそのままスコアになります。

The task

課題

The agent takes the seat of a contestant in a performance tuning contest. It starts with:

  • the specification of ISUMAIL, a newsletter delivery service, written in Japanese
  • a reference implementation in Go and PostgreSQL that works but is slow
  • root access to the three servers it runs on, which differ in CPU and memory

エージェントは、チューニングコンテストの参加者と同じ立場に置かれます。最初に渡されるのは次の3つです。

  • ニュースレター配信サービス「ISUMAIL」の仕様書（日本語）
  • GoとPostgreSQLで書かれた、動くけれど遅い参照実装
  • それが動いている3台のサーバーのroot権限。CPUもメモリも1台ずつ違う

Anything may change: queries and indexes, caching, the architecture, the language, the database, which server does what. The only condition is that the service keeps behaving as the specification says.

A load test plays the users. Publishers schedule issues, which must reach every subscriber before a deadline; readers open, click, share and subscribe. The score counts the mail delivered in time and the activity that succeeded. Inconsistent data fails the test.

何を変えても構いません。SQLやインデックス、キャッシュ、アーキテクチャ、言語、データベース、サーバーの役割分担まで自由です。条件は、仕様どおりに動き続けることだけです。

ベンチマーカーは利用者の役をします。発行者は号を予約し、その号は期限までに購読者全員へ届かなければなりません。読者は開封、クリック、共有、購読をします。点は、期限内に届いたメールと成功した操作の数で決まります。データに不整合があればその回はFAILです。

Doing well takes several skills at once:

  • reading an unfamiliar specification and codebase
  • finding the bottleneck by measuring it
  • carrying a large rewrite through without breaking behavior
  • operating servers: deployment, recovery after a reboot, durable data
  • judgment under a budget: when to spend a load test, and when to stop taking risks

高い点を取るには、次の力が同時に要ります。

  • 初めて見る仕様書とコードを読み解く
  • 計測してボトルネックを見つける
  • 大きな書き換えを、動作を壊さずにやり切る
  • サーバーを運用する。配置、再起動後の復帰、データの永続化
  • 限られた回数の中で、いつ測り、どこで攻めるのをやめるかを決める

Where the format comes from

ISUCONについて

The format is borrowed from ISUCON (Iikanji ni Speed Up Contest, roughly "speed it up nicely"), a web performance tuning contest held in Japan since 2011. Teams of up to three engineers get the same deal: an unfamiliar slow service, a few servers and eight hours. The highest score at the end wins.

Past ISUCON problems and their solutions are public, so a model may have seen them solved. isu-bench is therefore scored on ISUMAIL, a problem in the same style written for it. Its source is not published and it ships only as machine images.

課題の形式はISUCONにならっています。ISUCONは2011年から続くWebアプリケーション高速化コンテストで、最大3人のチームが、初めて見る遅いWebサービスと数台のサーバーを渡され、8時間でどこまで速くできるかを競います。

過去のISUCONの問題と解法は公開されているので、モデルが解かれた例を見ているかもしれません。そこでisu-benchは、同じ形式で新しく作った問題「ISUMAIL」で採点します。ソースは公開せず、マシンイメージでだけ配布しています。

Scoring and rules

採点とルール

  • Score: the points of the {RUNS}th load test, divided by the estimated maximum of {WINNER}.
  • Every load test counts toward the {RUNS}, failed ones included.
  • After the last one the three servers are rebooted. If the service does not come back with the data written during that test, the score is 0.
  • No time limit. An agent that stops early is told to continue, up to three times.
  • No web access. Search tools are off and the network reaches only the model API, package registries and the servers.
  • One trial per configuration, in Go. A configuration is a model, the agent it runs in and a reasoning effort.
  • スコア: {RUNS}回目のベンチマークの点を、理論上の上限の見積もり（{WINNER}点）で割った値。
  • ベンチマークはFAILも含めてすべて{RUNS}回のうちに数えます。
  • 最後の1回の後に3台のサーバーを再起動します。サービスが復帰しない、またはその回に書き込んだデータが残っていなければ0点です。
  • 時間制限はありません。途中で止まったエージェントには、3回まで続行を指示します。
  • Webは使えません。検索ツールは無効で、通信先はモデルのAPI、パッケージレジストリ、サーバーだけです。
  • 1構成につき1試行、言語はGo。構成は、モデル、それを動かすエージェント、推論の強さの組み合わせです。

The full rules, the exact prompt and the harness are in the repository.

ルールの全体、プロンプトの原文、ハーネスはリポジトリにあります。

Caveats

注意点

  • Each configuration ran once, so the spread between trials is not measured. The untouched service alone varies by about 5% from test to test. Small gaps mean little.
  • Each model runs in its vendor's own agent, so a result belongs to the pair, not to the model alone.
  • The maximum is an estimate of the problem's theoretical limit. Its derivation is withheld together with the source, to keep the problem out of training data.
  • 各構成の試行は1回だけで、試行間のばらつきは測っていません。手を入れる前のサービスでも、点は回ごとに5%ほど変わります。小さな差に意味はありません。
  • モデルはそれぞれ提供元のエージェントで動かしています。結果はモデル単体ではなく、その組み合わせのものです。
  • 上限は問題の理論上の限界を見積もった値です。導き方は、ソースと同じく学習データに入れないため公開していません。
